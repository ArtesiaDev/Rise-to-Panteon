# Feature Specification: DOTS Audit & Refactor

**Feature Branch**: `001-dots-audit-refactor`
**Created**: 2026-03-01
**Status**: Draft
**Input**: Аудит и рефакторинг DOTS-миграции: проверка best practices, поиск неточностей и улучшений, имплементация исправлений

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Аудит DOTS best practices и обновление миграционного плана (Priority: P1)

Как разработчик, я хочу провести полный аудит текущей DOTS-реализации относительно официальных best practices Unity Entities 1.4, чтобы убедиться что кодовая база не содержит антипаттернов, скрытых проблем производительности и архитектурных ошибок. Результатом должен быть обновлённый миграционный план с зафиксированными отклонениями и рекомендациями.

**Why this priority**: Без качественного аудита невозможно определить объём работ по рефакторингу. Это фундамент для всех последующих улучшений.

**Independent Test**: Можно полностью протестировать, проверив что аудит-отчёт покрывает все 24 системы, 33 компонента, 4 asmdef, и содержит конкретные рекомендации с приоритетами.

**Acceptance Scenarios**:

1. **Given** текущая DOTS-кодовая база (87 файлов), **When** проводится аудит, **Then** каждая система проверена на: [BurstCompile], ISystem vs SystemBase, SystemAPI vs EntityManager, корректное использование ECB, правильные system ordering атрибуты
2. **Given** миграционный план (Docs/DOTS_Migration_Plan.md), **When** сравниваем план с реализацией, **Then** все отклонения задокументированы в разделе 11 плана с обоснованием
3. **Given** результаты аудита, **When** формируется список улучшений, **Then** каждое улучшение имеет приоритет (critical/high/medium/low), описание проблемы и рекомендуемое решение

---

### User Story 2 - Исправление критических и высокоприоритетных проблем (Priority: P2)

Как разработчик, я хочу исправить все найденные критические и высокоприоритетные проблемы в DOTS-коде, чтобы кодовая база полностью соответствовала best practices и была готова к production.

**Why this priority**: Критические проблемы (если найдены) могут приводить к крашам, утечкам памяти или некорректному поведению. Высокоприоритетные — к проблемам производительности.

**Independent Test**: Можно протестировать запуском игры с разными seed (42, 12345, 999999) и проверкой что геймплей не изменился, нет ошибок в консоли, нет утечек памяти.

**Acceptance Scenarios**:

1. **Given** список критических проблем из аудита, **When** применяются исправления, **Then** все системы компилируются без ошибок, Burst compilation проходит успешно
2. **Given** исправленный код, **When** запускается игровой цикл с seed=42, **Then** поведение игры идентично до рефакторинга (карта, спавн, AI, комбат, лут)
3. **Given** исправленный код, **When** проверяется консоль Unity, **Then** отсутствуют ошибки и Burst-fallback предупреждения

---

### User Story 3 - Применение средне- и низкоприоритетных улучшений (Priority: P3)

Как разработчик, я хочу обновить миграционный план и задокументировать все обоснованные отклонения от DOTS best practices, чтобы документация отражала актуальное состояние кодовой базы после рефакторинга.

**Why this priority**: Документация должна соответствовать коду. Аудит не выявил проблем со стилем, именованием или запросами — только отсутствие [BurstCompile] на методах и использование EntityManager вместо SystemAPI.

**Independent Test**: Можно проверить ревью кода — каждое улучшение должно соответствовать конституции проекта и не менять поведения.

**Acceptance Scenarios**:

1. **Given** список средне/низкоприоритетных улучшений, **When** применяются изменения, **Then** код компилируется, тесты проходят, геймплей не изменён
2. **Given** улучшенный код, **When** проводится повторный аудит, **Then** все пункты чеклиста best practices отмечены как пройденные

---

### Edge Cases

- Что происходит если Burst-компиляция системы невозможна из-за использования EntityManager? Система должна быть явно задокументирована с обоснованием отсутствия [BurstCompile]
- Что если рефакторинг системы ломает порядок выполнения? Все [UpdateAfter]/[UpdateBefore] атрибуты должны быть проверены и скорректированы
- Что если улучшение требует изменения публичного API компонентов? Все зависимые системы и мосты должны быть обновлены синхронно

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Аудит ДОЛЖЕН покрывать все файлы в Assets/_Project/Dots/ (Runtime, Hybrid, Authoring, Baking)
- **FR-002**: Каждая система ДОЛЖНА быть проверена по чеклисту: [BurstCompile], ISystem, SystemAPI, ECB usage, system ordering, RequireForUpdate
- **FR-003**: Каждый компонент ДОЛЖЕН быть проверен на: отсутствие managed полей, корректное использование IEnableableComponent, правильные buffer capacities
- **FR-004**: Assembly definitions ДОЛЖНЫ быть проверены на: корректные зависимости, отсутствие циклических ссылок, правильные noEngineReferences
- **FR-005**: Рефакторинг НЕ ДОЛЖЕН менять геймплейную логику — поведение с seed 42, 12345, 999999 должно оставаться идентичным
- **FR-006**: Все изменения ДОЛЖНЫ компилироваться без ошибок и проходить Burst-компиляцию (где применимо)
- **FR-007**: Миграционный план (DOTS_Migration_Plan.md) ДОЛЖЕН быть обновлён с учётом результатов аудита
- **FR-008**: Каждое отклонение от DOTS best practices ДОЛЖНО быть либо исправлено, либо задокументировано с обоснованием

### Key Entities

- **System**: ECS-система (ISystem) — обрабатывает компоненты в каждом тике. Ключевые атрибуты: Burst-совместимость, группа выполнения, зависимости от других систем
- **Component**: Данные сущности (IComponentData) — хранит состояние. Ключевые атрибуты: unmanaged-only, enableable/buffer support
- **Assembly Definition**: Граница компиляции — определяет зависимости между модулями
- **Migration Plan**: Документ архитектурных решений — фиксирует отклонения и обоснования

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% систем проаудированы и задокументированы в отчёте (24 из 24)
- **SC-002**: 100% компонентов проверены на соответствие best practices (33 из 33)
- **SC-003**: 0 критических проблем остаётся после рефакторинга
- **SC-004**: Игра запускается и работает корректно на 3 тестовых seed (42, 12345, 999999) после всех изменений
- **SC-005**: Консоль Unity не содержит ошибок и Burst-fallback предупреждений в runtime
- **SC-006**: Миграционный план обновлён и отражает актуальное состояние кодовой базы

## Assumptions

- Текущая кодовая база уже функционирует корректно (шаги 1-7 миграции завершены)
- Геймплейные механики заморожены — никаких новых фич в рамках этого рефакторинга
- Unity 2022.3 LTS и Entities 1.4.x — версии не меняются
- Гибридный подход (ECS + GameObject rendering) остаётся неизменным
- Тестирование производится вручную через запуск с тестовыми seed
