# Rise to Panteon — Конституция проекта

## Основные принципы

### I. DOTS-First архитектура

Вся игровая логика ДОЛЖНА быть реализована через Unity DOTS
(Entities 1.4.x). Компоненты — чистые `struct IComponentData` без
managed-полей. Системы — `partial struct : ISystem`. GameObject и
MonoBehaviour допускаются ТОЛЬКО в Hybrid-слое (ввод, рендеринг,
UI) и НИКОГДА не содержат игровую логику.

**Обоснование**: единый путь данных гарантирует совместимость с
Burst, масштабируемость и предсказуемость поведения.

### II. Разделение Simulation и Presentation

Проект строго разделён на четыре assembly:

- **Runtime** — компоненты и системы симуляции (без UnityEngine
  ссылок где возможно)
- **Hybrid** — мосты между ECS и GameObject (Input, Tilemap,
  Sprite, UI, Camera, Gizmos)
- **Authoring** — MonoBehaviour + Baker для конвертации данных
  дизайна
- **Baking** — дополнительные BakingSystem расширения

Hybrid ЗАВИСИТ от Runtime, но Runtime НЕ ДОЛЖЕН зависеть от
Hybrid. Данные текут в одном направлении: Input Bridge → ECS
Simulation → Presentation Bridges.

**Обоснование**: однонаправленный поток данных упрощает отладку,
позволяет тестировать симуляцию изолированно и заменять рендеринг
без изменения логики.

### III. Детерминизм симуляции

Вся симуляция ДОЛЖНА быть детерминирована по seed. Используется
ТОЛЬКО `Unity.Mathematics.Random`. Системы в
`FixedStepSimulationSystemGroup` выполняются в строго
фиксированном порядке. Запрещено использование
`UnityEngine.Random`, `System.Random`, `Time.deltaTime` внутри
симуляции.

**Обоснование**: детерминизм позволяет воспроизводить баги,
гарантирует одинаковый опыт при одном seed и упрощает тестирование.

### IV. Burst-производительность

Все системы симуляции ДОЛЖНЫ компилироваться с `[BurstCompile]`.
Если `[BurstCompile]` невозможен (например, прямой вызов
`EntityManager` в OnUpdate), система ДОЛЖНА содержать комментарий
с обоснованием отсутствия атрибута (см. MapGenerationSystem как
образец). Компоненты НЕ ДОЛЖНЫ содержать managed-типов (string,
class, массивы). Для коллекций — `NativeArray`, `NativeList`,
`BlobAssetReference`. Для строковых данных — `FixedString`.

**Обоснование**: Burst обеспечивает нативную производительность;
нарушение ограничений ведёт к fallback на Mono и деградации FPS.
Комментарий при отсутствии Burst предотвращает неосознанные
пропуски атрибута.

### V. Дисциплина порядка систем

Каждая система ДОЛЖНА явно декларировать свою группу через
`[UpdateInGroup]` и зависимости через `[UpdateAfter]` /
`[UpdateBefore]`. В `OnCreate` — `RequireForUpdate<T>()` для
singleton-зависимостей (MUST) и для query-компонентов (SHOULD —
data-driven queries автоматически пропускаются при отсутствии
совпадений). В `OnUpdate` — ранний выход (`return`) если данные
не готовы.

Текущий порядок Fixed-систем (14 шт.) является каноническим и
изменяется ТОЛЬКО с обоснованием и обновлением документации.

**Обоснование**: неявный порядок систем — главный источник
трудноуловимых багов в ECS; явные зависимости делают поведение
предсказуемым.

### VI. Простота (YAGNI)

Не добавлять абстракции, паттерны или функциональность «на
будущее». Каждый компонент, система и мост ДОЛЖНЫ решать
конкретную текущую задачу. Три похожих строки кода лучше
преждевременной абстракции. Сложность ДОЛЖНА быть обоснована в
PR/коммите.

**Обоснование**: проект активно мигрирует на DOTS; лишние
абстракции замедляют итерации и усложняют рефакторинг.

## Технические ограничения

- **Unity**: 2022.3 LTS + Entities 1.4.x + URP 2D
- **Рендеринг**: Hybrid (Tilemap + SpriteRenderer), НЕ DOTS
  Graphics
- **Карта**: процедурная генерация конфигурируемого размера
  (default ~50×70) через BlobAsset, количество комнат
  рассчитывается автоматически по DensityFactor
- **Навигация**: A* в EnemyPathfindSystem с occupancy grid
- **Языки кода**: C# (.NET Standard 2.1)
- **Комментарии**: русский язык для inline-комментариев и
  документации
- **Именование**: PascalCase для публичных типов; суффиксы
  `System`, `Config`, `State`, `Tag`; namespace
  `RuntimeRoguelike.Dots.*`
- **Структурные изменения**: через `EntityCommandBuffer`, никогда
  напрямую в итерации

## Рабочий процесс разработки

- Новая функциональность начинается с компонентов (данные), затем
  система (логика), затем мост (визуализация)
- Коммиты — атомарные: один коммит = одна логическая единица
  изменений
- Перед мержем — проверка компиляции Burst и отсутствия
  managed-утечек в Runtime assembly
- Рестарт игры — без перезагрузки сцены (новый seed, пересоздание
  entities)
- Singleton-компоненты используются для глобального состояния
  (`RunState`, `InputState`, `DifficultyState` и др.)
- **Документация механик** (NON-NEGOTIABLE): при любом изменении
  геймплейной механики ОБЯЗАТЕЛЬНО обновить документацию:
  - Индекс: `Docs/RuntimeRoguelike_CurrentMechanics.md`
  - Детали: `Docs/Mechanics/<НазваниеМеханики>.md`
  - Новая механика → новый файл + строка в таблицу индекса
  - Удалённая механика → удалить файл + строку из таблицы

## Governance

Конституция является высшим руководящим документом проекта. Все
архитектурные решения ДОЛЖНЫ соответствовать принципам выше.

**Процедура изменений**:
1. Предложение изменения с обоснованием
2. Обновление конституции с инкрементом версии (SemVer)
3. Обновление зависимых шаблонов (plan, spec, tasks)
4. Коммит с описанием `docs: amend constitution to vX.Y.Z`

**Версионирование**:
- MAJOR — удаление или несовместимое изменение принципа
- MINOR — новый принцип или существенное расширение
- PATCH — уточнения формулировок, исправление опечаток

**Соответствие**: каждый PR/review проверяется на соблюдение
принципов. Нарушения допускаются ТОЛЬКО с явным обоснованием и
планом миграции.
