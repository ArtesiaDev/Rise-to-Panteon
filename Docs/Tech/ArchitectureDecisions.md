## Рекомендовано

### R-01. Сущности создаются в рантайме, без SubScenes
SubScenes и baking не используются: визуал через них не идёт (A-04), а конфиги должны обновляться без пересборки (A-07), то есть всё равно строятся в рантайме. ECS-мир наполняется из трёх источников: конфиги (JSON → BlobAssets), генерация мира по сиду, сохранения. «Префабы» сущностей — архетипы, собранные кодом по данным конфигов.

### R-02. Контуры и контракт между ними
Три контура:
- **Симуляция** — ECS, Burst-джобы. Знает только данные. Не знает про ассеты, GameObject'ы, UI, время кадра.
- **Представление** — ООП, VContainer, URP 2D, Addressables. Рисует, анимирует, играет звук и VFX.
- **Сервисы** — ООП, VContainer: сохранения, конфиги, загрузка контента, платформа, позже сеть.

Контракт — только данные, в обе стороны:
- **Симуляция → представление.** В конце тика Burst-джоб экспорта пишет компактный снимок `ViewState { StableId, ViewKey, позиция, направление, анимационное состояние, флаги }` и поток событий (удар, смерть, поглощение, звук) в двойной буфер. Представление читает его через сервис `IWorldView`, сравнивает по `StableId` (появился / исчез / изменился), интерполирует между двумя последними тиками. `ViewKey` — id из каталога визуалов в конфигах; каталог сопоставляет его с адресом Addressables.
- **Ввод, UI, сервисы → симуляция.** Только команды: ввод за тик (`PlayerInput`) и очередь операций (O-паттерн из R-04). Мостовая система вливает их в ECS в начале фиксированного тика.
- **UI** читает read-модели (статы игрока, инвентарь, карта), которые экспорт пишет рядом со снимком.
- Ни один MonoBehaviour не обращается к `EntityManager`.

Почему так: контуры тестируются по отдельности; нет «костылей» вида поиска сущностей из вьюх; при появлении сервера представление можно кормить снимками с сервера вместо локальной симуляции (как карта в продакшне: дельты по WebSocket → клиентский мир → вьюхи).

### R-03. Хост ECS-мира и DI
- Автосоздание мира выключено (`UNITY_DISABLE_AUTOMATIC_SYSTEM_BOOTSTRAP_RUNTIME_WORLD`, `[assembly: DisableAutoCreation]`). Мир создаёт и уничтожает сервис-хост из корня VContainer: явный список систем, включая `UpdateWorldTimeSystem` и ECB-системы, встраивание в PlayerLoop и удаление из него.
- Мостовые системы (`SystemBase`) создаёт VContainer с зависимостями в конструкторе, хост добавляет их в мир. Хелперы интеграции VContainer вида `*DefaultWorld*` не используются: они опираются на `DefaultGameObjectInjectionWorld`.
- Игровой код не читает `World.DefaultGameObjectInjectionWorld`. Присвоить его допустимо только ради редакторных инструментов (Hierarchy, Inspector).
- Burst-системы (`ISystem`) не внедряются и сервисов не вызывают — только данные.

### R-04. Готовность к серверу
Правила, которые держат открытыми оба варианта сервера (O-02):
1. Всё авторитетное состояние — unmanaged-компоненты и буферы.
2. Симуляцию двигают только `PlayerInput` и очередь операций; системы не читают `Input`, `Time`, камеру.
3. Один фиксированный тик, своя группа симуляции.
4. Побочные эффекты — события-данные для представления; симуляция идемпотентна.
5. Нет статического доступа к миру; миров может быть несколько.
6. `StableId` (ulong, диапазоны по источнику создания) на всём, что сохраняется или адресуется; `Entity.Index` недетерминирован и для этого не годится.
7. Операция = `{type, seq, tick, seed, payload}`, цепочка Validate → Apply → Log, операция не порождает операцию.
8. Авторитетные числа — целые или fixed-point; float — движение и визуал.
9. Порядок, где он важен, — по `StableId` (сортировки в Collections нестабильны).
10. Сохранение — версионированные DTO, не `SerializeUtility`.

Детерминизм: `FloatMode.Deterministic` в Burst работает только в Burst-коде и только на 64-бит. Значит, Android — только ARM64. С .NET побитового совпадения float нет.

### R-05. Стек представления
- **Анимация существ:** Spine 4.3 Professional (скины и аттачи под эволюцию форм, кости не GameObject'ы, анимация в рабочих потоках, управление из кода удобно агентам) или бесплатный Unity 2D Animation 16 на CPU/Burst (GPU-деформация на Android GLES3 не работает). Нужен спайк: 40 скелетов с 2D-светом на слабом Android. Открыто — O-05.
- **Пол:** меши-чанки, сгенерированные из карты, с шейдером смешивания текстур и маленькой текстурой состояния клеток (следы, трещины, распад — «мир помнит» без лишних объектов). Для прототипа допустим Tilemap.
- **Стены, пропсы, следы:** спрайты с Y-сортировкой из атласов; вариации через Renderer Shader User Value без поломки батчинга.
- **Свет:** Global + 8–12 небольших Spot/Freeform, одна blend style, масштаб light texture ≤ 0.5, тени у 1–3 источников, blob-тени под существами, уровни качества.
- **Силуэты за стенами и туман войны:** свой проход Render Graph для 2D-рендерера.
- **VFX:** Particle System (Shuriken) с Sprite-Lit и Shader Graph; VFX Graph не использовать (мобильные).
- **Пост-обработка:** Dual/Kawase bloom, цветокоррекция через LUT, виньетка, один свой проход искажения по краям экрана.
- **Батчинг:** SRP Batcher, без MaterialPropertyBlock, атласы по биому или виду, Tight-меши спрайтов.
- **Android:** ARM64, Vulkan с запасным GLES3.

### R-06. UI — UI Toolkit
UI Toolkit (PanelRenderer вместо устаревшего в 6.5 UIDocument, data binding, пакет Localization). Причины: UXML и USS — текст, их надёжно пишет агент (префабы uGUI — YAML с GUID и якорями); встроенный UI-агент Unity генерирует только UI Toolkit; в 6.x есть шейдеры для UI, SVG, фильтры, анимация текста. Риски: официальная таблица Unity для runtime всё ещё пишет «рекомендуется uGUI»; частицы внутри UI — только через RenderTexture; safe area — свой контейнер. uGUI — только в исключениях. Маркеры над существами (опасность, HP) — спрайты в мире, не UI.

### R-07. Ассеты
Addressables 2.11 (или 4.0 ради await) за собственным интерфейсом провайдера ассетов с подсчётом ссылок, как в продакшне. Новые Content Directories (6.6) — формат сборки под тем же API, пока только локальный; переход после спайка. Симуляция к Addressables не обращается.

### R-08. Конфиги: путь от файла до ECS
1. `Configs/` (submodule): `manifest.json`, `schemas/*.schema.json` (JSON Schema 2020-12), `data/*.json`, `tools/` (форматтер, валидатор), CI в конфиг-репо: формат → схема → смысловые проверки (уникальные id, ссылки между таблицами).
2. C#-DTO генерируются из схем.
3. Сборка игры упаковывает конфиги в версионированный пак с хешем (формат — O-08).
4. Сервис конфигов (ООП) при старте проходит цепочку источников: скачанный пак (позже, с сервера или CDN) → встроенный пак; проверяет версию схемы и хеш, как `getVersions` в продакшне.
5. Парсинг → DTO → BlobAssets → синглтоны ECS через мостовую систему. Подмена конфигов — только между сессиями.
6. В редакторе конфиги читаются прямо из `Configs/` с горячей перезагрузкой.
7. Синглтон `ConfigVersion` (версия схемы, SHA коммита, хеш) пишется в сохранения и логи.
8. Новая таблица = схема + данные + конвертер в blob. В продакшне — 10–12 ручных правок в 4–5 репозиториях.

### R-09. Сохранения
По GDD (M01): полный снимок мира, атомарная запись (временный файл → замена) с одной резервной копией, вне главного потока; при сворачивании — пауза и автосохранение. Формат — версионированные DTO, те же, что позже станут авторитетным документом на сервере.

### R-10. Производительность
По умолчанию — Burst-джоб (`IJobEntity`/`IJobChunk`, `ScheduleParallel`); главный поток — только с обоснованием. Структурные изменения — пачками через ECB в отведённых точках. Пространственная сетка для поиска соседей. Детали — `JobsAndBurst.md`. Бюджеты из GDD: 30–40 активных существ на локацию, 40 в одной комнате без просадки FPS на слабом телефоне; переход между локациями ≤ 1 с (≤ 2 с на слабых), догонка шага мира ≤ 100 мс.

### R-11. Процесс агентов (отложено до обсуждения харнесса)
Из продакшна взять: конституцию «один принцип — один файл», базу знаний со строгим форматом и валидатором, единый вход в задачу, ревью «скептик + инженер», проверку компиляции и тесты. Не брать: десятки пересекающихся скиллов, две конституции, регистрацию фич правкой центральных файлов, ручное дублирование валидации клиента и сервера.
