## Рекомендовано

### R-01. Контент в ECS
- Основной путь Unity в 6.6 не изменился: SubScenes → Bakers → unmanaged-компоненты, BlobAssets для неизменяемых данных.
- Ссылки на ассеты, которые всегда в памяти: `UnityObjectRef<T>` (замена managed-компонентов, которые в 6.6 объявлены устаревшими).
- Загрузка по требованию: `WeakObjectReference<T>`, `WeakObjectSceneReference`, `EntityPrefabReference` + `RuntimeContentManager`. Контент-архивы Unity строит из сабсцен сама.
- Большой мир: регион = сабсцена с секциями, загрузка через `EntitySceneReference`. Состояние, которое переживает выгрузку региона (бродячие существа), не держать в `SceneSection` региона — иначе оно удалится вместе с ним.
- «ECS for all» (сущности в обычных сценах, baking без сабсцен, GameObject = Entity) пока **не выпущено**, только анонсировано. Baking по-прежнему только в SubScenes.

### R-02. Addressables
- Документация Entities прямо говорит: Resources, AssetBundles и Addressables для ECS-данных «не работают или неоптимальны», лучшая практика — контент-архивы Entities.
- Рекомендация: контент ECS-контура — только через Entities content management. Addressables (или новые Content Directories из 6.6) — запасной путь для того, что не ложится в ECS: окна UI, часть аудио, инструменты.
- Один ассет не должен одновременно грузиться из сабсцены и из Addressables — он попадёт в билд дважды.

### R-03. Представление (2D)
- Entities Graphics 6.6 **не поддерживает** URP 2D Renderer, спрайты, Tilemap и 2D-свет. `SpriteRenderer` — только компаньон, Tilemap и Light2D при запекании вырезаются. Официальных 2D-сэмплов на ECS нет.
- Поэтому визуальный контур гибридный по необходимости: ECS-системы в `PresentationSystemGroup` решают, что и где показать, и управляют пулом GameObject'ов (SpriteRenderer, Animator, Light2D) через `UnityObjectRef<GameObject>`. Это паттерн из документации Unity. Тайлы — Tilemap в обычной сцене, заполняемый из данных карты ECS.
- Симуляция — в фиксированном шаге, интерполяцию для отрисовки пишем сами.
- Unity Physics — только 3D, для 2D Unity предлагает низкоуровневый Box2D v3 (`LowLevelPhysics2D`) или собственную сетку/пространственный индекс.

### R-04. Внедрение зависимостей
- В Entities встроенного DI нет. Официальные механизмы: синглтоны, компоненты на системах, `CreateAfter` + `GetExistingSystem`, `ICustomBootstrap`.
- VContainer 1.19: интеграция с ECS в статусе beta, внедряет только в `SystemBase`. Burst-системы (`ISystem`) не внедряются в принципе. Совместимость с 6.6 надо проверить отдельно.
- Рекомендация — сочетать:
  - VContainer — корень композиции: бутстрап, ООП-сервисы (сохранения, загрузка контента, аудио, платформа, позже сеть), UI; создаёт и владеет ECS-миром.
  - Небольшое число мостовых систем на `SystemBase` с внедрёнными сервисами переводят данные между сервисами и ECS (компоненты-запросы и компоненты-ответы).
  - Burst-системы симуляции сервисов не вызывают и общаются только данными. Игровые правила — не сервисы, а статические чистые функции (см. R-05).

### R-05. Готовность к серверу
Возможны два будущих сервера: (а) Unity dedicated server с Netcode for Entities — тот же ECS-код, в 6.6 это core-пакет, в 6.7 он снова станет отдельным с ломкой API; (б) отдельный .NET-сервис, как в продакшне. Entities вне Unity не работает, поэтому для (б) общим может быть только «ядро правил» на чистом C#.

Правила, которые держат открытыми оба пути:
1. Всё авторитетное состояние — в unmanaged-компонентах и буферах. Ничего влияющего на геймплей в MonoBehaviour, Physics2D или статиках.
2. Симуляцию двигают только данные ввода (компонент ввода за тик) и очередь операций (дискретные действия). Системы не читают `Input`, `Time`, камеру.
3. Один фиксированный тик, своя группа симуляции внутри fixed-step.
4. Побочные эффекты (VFX, звук, UI) — события-данные, которые читает представление. Симуляция идемпотентна.
5. Никакого статического доступа к миру (`World.DefaultGameObjectInjectionWorld`). Мосты получают свой мир.
6. `StableId` (ulong, диапазоны по источнику создания) на всём, что сохраняется или адресуется. Операции, сохранения, логи ссылаются только на `StableId`, не на `Entity`.
7. Операция = `{type, seq, tick, seed, payload}`, цепочка Validate → Apply → Log, операция не порождает операцию, `seq` = ревизия.
8. Ядро правил — отдельная сборка на чистом C# (`noEngineReferences`, без Collections), статические функции над blittable-структурами, вызываемые из Burst и компилируемые на сервере. Покрыто golden-тестами.
9. Авторитетные числа — целые или fixed-point, float — только движение и визуал. Свой ГСЧ (PCG32/SplitMix) в ядре, сид = hash(worldSeed, stableId, tick). Порядок, где он важен, — по `StableId`.
10. Сохранение — версионированные DTO (снимок + seq + хвост операций + хеш), не `SerializeUtility` (он ломается при любом изменении компонентов и не читается сервером).

Детерминизм: `FloatMode.Deterministic` в Burst даёт совпадение между платформами только для Burst-кода и только на 64-бит; с .NET-сервером побитового совпадения по float нет. Поэтому модель «сервер повторяет операцию и отклоняет при расхождении» реалистична для целочисленных правил (урон, эссенции, предметы, шаг мира), но не для real-time боя с float-движением.

### R-06. Конфиги
- **Формат — JSON**, а не YAML: нативная поддержка в JSON Schema, в веб-админке и на .NET-сервере, нет ловушек неявной типизации YAML. Вместо комментариев — поле `note`. Файлы всегда пишет один форматтер.
- **Контракт — JSON Schema 2020-12**, одна схема на таблицу, ограниченное подмножество ключевых слов. Из схем генерируются C#-DTO, по ним же админка построит формы и таблицы.
- **Репозиторий — git submodule** в корне проекта (`Configs/`), вне `Assets/`, чтобы Unity не создавала `.meta`. Подмодуль фиксирует коммит — билды воспроизводимы; ветку для теста переключают `git -C Configs switch`.
- **Путь в ECS:** редакторный импортёр читает `Configs/` → проверка → ScriptableObject-база → Baker в конфиг-сабсцене → BlobAssets → unmanaged-синглтоны, читаемые из Burst. Позже — скачиваемые конфиги тем же конвертером, подмена между забегами.
- **Формулы:** кривые роста считаются при экспорте (админкой), формула хранится рядом, CI пересчитывает и сверяет. Формулы, зависящие от состояния игры, — только маленькая безопасная грамматика, компилируемая в байткод для Burst; тот же интерпретатор на сервере. Никакого кода в конфигах.
- **Версия:** синглтон `ConfigVersion` (версия схемы, SHA коммита, хеш) пишется в сохранения и логи.
- **Цель по трудоёмкости:** новая таблица — схема + данные + конвертер в blob. В продакшне это 10–12 ручных правок в 4–5 репозиториях.

### R-07. Документация по ECS
Устарело относительно 6.6: `Entities.ForEach`, `Job.WithCode`, Aspects (удалены в 6.5); managed-компоненты и managed shared-компоненты (устарели в 6.6); `PlaybackPolicy`; описание placeholder-сущностей в ECB; `PostLoadCommandBuffer` → `ImportEntity`; InstanceID → 64-битный `EntityId`; `GetComponentObject` → `GetCompanion`. `UnityPhysics.md` для 2D-проекта неактуален. Рекомендация — переписать справочники по руководствам 6.6.

### R-08. Процесс агентов (что взять из продакшна и чего избежать)
- Взять: конституцию «один принцип — один файл» с индексом; базу знаний с жёстким frontmatter, обязательными разделами и валидатором индекса; единый вход в работу над задачей; ревью «скептик + инженер»; обязательную проверку компиляции и тесты «красный → зелёный»; срез фичи по слоям через `.asmref`; граф загрузки с явными зависимостями; провайдер ассетов с подсчётом ссылок.
- Не брать: десятки пересекающихся скиллов-входов; две параллельные конституции; артефакты задач в истории репозитория инструментов; регистрацию фич правкой центральных файлов; дублирование валидации клиента и сервера вручную.
