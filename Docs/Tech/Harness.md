# Харнесс агентов

> Как агенты работают в этом репозитории: где лежит знание, как его найти, как писать документы и заметки к коду,
> кто и чем проверяет работу. Правила `DOC-xx` и `WORK-xx` обязательны для агентов и проверяются ревьюером.
> Точка входа Claude Code — `CLAUDE.md`, Codex — `AGENTS.md` со ссылкой на общие правила `CLAUDE.md`.
> Процесс задают правила `WORK`, инструменты — общая база `rag` и ревьюер; подключение Codex описано в §13.

## 1. Слои знаний

| Уровень | Что | Где | Слой в базе |
|---|---|---|---|
| 0 | Маршрутизатор и жёсткие правила | `CLAUDE.md`; вход Codex — `AGENTS.md` | — |
| 1 | Видение игры; каркас кода | `Docs/GDD/README.md`; `Docs/Tech/Architecture/README.md` | `gdd`, `arch` |
| 2 | Игровые системы; контуры кода | `Docs/GDD/<Система>.md`; `Docs/Tech/Architecture/<Контур>.md` | `gdd`, `arch` |
| 3 | Фича; срез | `Docs/GDD/Features/<ID>-<Name>.md`; шапка заметки среза | `gdd-feature`, `note` |
| 4 | Конкретный код | Заметки к коду (`CodeStructure.md` §6.4) | `note` |
| — | Термины, формулы | `Docs/GDD/Glossary.md`, `Docs/GDD/Formulas.md` | `gdd-reference` |
| — | API Entities, Jobs, Burst 6.6 | `Docs/Tech/Reference/Unity/` | `reference` |
| — | Статус реализации | `Docs/Roadmap.md` | `roadmap` |
| — | Как работают агенты | этот документ | `harness` |

Вне базы: `Docs/Parked/` (отложенные механики, не источник истины), `Docs/References/` (изображения),
`Docs/Tech/Reference/WO_*.md` (чужой проект), код прототипа `Assets/_Project/{Dots,Framework,Main,Dev,Editor,Data}`.

Приоритет при расхождении: что делает игра — GDD (файл фичи → документ системы); как устроен код — архитектура
(`README.md` → документ контура → справочники). Заметка описывает код и не меняет правила: если
заметка или код противоречат GDD или архитектуре — это дефект.

## 2. Поиск — MCP-сервер `rag`

Весь корпус (GDD ~2,5 МБ, архитектура ~0,4 МБ) в контекст не помещается. Агент не читает документы целиком «на
всякий случай», а берёт нужное через `rag`:

| Инструмент | Когда | Как работает |
|---|---|---|
| `context_for_paths(paths)` | Перед правкой или созданием файлов | Детерминированно, без векторов: запись заметки о типе, шапка среза (владелец GDD, участие, зависимости), правила GDD из записи, документ контура, правила `ARCH`, `CODE` и контура; для документов — слой, связи и правила `DOC`. Файл может ещё не существовать: для нового среза берётся строка `CodeStructure.md` §7.4 |
| `search(query, layers, k)` | «Как устроено, где, почему», незнакомая область | Векторы (bge-m3) + BM25 со стеммингом, слияние рангов; прямые попадания по ID правил и фич; связанные документы по графу |
| `get(ref)` | Нужен точный текст | Правило (`ARCH-06`, `SIM-03`, `DOC-02`, `E01 R3`), фича (`E01`), документ (путь или имя), раздел (`Simulation.md#Шаг мира`), тип кода (`AbsorbSystem` → запись в заметке) |
| `related(ref, hops)` | Что ещё затронуто | Граф: markdown-ссылки, упоминания фич, шапки заметок (`gdd`, `participates`, `depends`) |
| `lint(changed, base)` | Перед коммитом, у ревьюера | Проверки §8 |

- Найденное — опора, а не замена чтению: код и файлы, которые меняются, агент читает сам; правило цитирует по ID
  через `get`.
- Индекс обновляется при каждом запросе и только для изменившихся файлов; отдельной регенерации документов нет:
  документ правит тот, кто меняет предмет. Почему: в продакшне генерация документов моделью по вебхуку давала
  выдуманные идентификаторы и дрейф.
- Те же команды — в терминале: `uv run --project Tools/rag rag <search|context|get|related|lint|index|eval> …`.

## 3. Заметки к коду

В коде нет комментариев (CODE-18). Всё знание о коде — что делает тип, какие правила GDD реализует, где
выполняется, что нельзя и почему, уроки исправленных багов — лежит в заметке его единицы: одна заметка на срез или
область инфраструктуры, запись `### <Тип>` на значимый тип, строка таблицы на простой. Формат — `CodeStructure.md`
§6.4, требования — CODE-18 и CODE-19.

Связь «файл → заметка» не зависит от дисциплины агента: хук показывает запись при чтении файла и напоминает о ней
при правке (§8), `rag lint` ловит код без записи и записи без кода, ревьюер сверяет запись с поведением кода.

## 4. Правила документов

| ID | Правило |
|---|---|
| DOC-01 | Каждый факт записан в одном месте. Остальные документы ссылаются на него — ID правила, ID фичи, путь и раздел, — а не пересказывают. Найден дубль — остаётся одно место, в остальных ссылка. Исключение — входные `CLAUDE.md` и `AGENTS.md`: каждый в своём агенте всегда в контексте и напоминает самые частые правила одной строкой с ID; норма и её оговорки — только в источнике. |
| DOC-02 | Документ описывает только текущее состояние. «Было», «стало», «раньше», «теперь», «больше не», «legacy» в описаниях не пишутся; история — в git. |
| DOC-03 | Без воды: ни вступлений, ни итогов, ни повторов, ни общих слов. Каждое предложение — факт, правило, число или причина. Обязательные детали не сокращаются. |
| DOC-04 | Что где пишется: механика — GDD; как устроен код и правила кода — архитектура; что делает конкретный код и почему — заметка; статус реализации — `Docs/Roadmap.md`; как работают агенты — этот документ. Почему принято неочевидное решение — строкой «Почему: …» рядом с ним; отвергнутый вариант механики — в «Отклонено» файла фичи. Отдельных журналов решений нет. Нерешённое — `Docs/GDD/OpenQuestions.md` (геймдизайн; вопросы одной фичи — в §12 её файла) и `Architecture/README.md` §7 (архитектура). |
| DOC-05 | Правила — таблицей `\| ID \| Правило \|` с префиксом документа (`ARCH`, `SIM`, `CODE`, `DOC` …). Правила GDD — `**Rn.**` в файле фичи. Выданный ID не меняется и не переиспользуется. |
| DOC-06 | Новые `.md` — только в местах из §8 (`MD-PLACE`). Планы, спецификации, отчёты сессий, разборы багов, заметки «на потом» в репозиторий не пишутся: результат работы — правка канонических документов. |
| DOC-07 | Ссылка на документ — относительная markdown-ссылка или путь либо имя файла в обратных кавычках (`Simulation.md` §5); на правило — по ID, на фичу — по ID GDD. Оба вида ссылок `rag` превращает в связи графа, markdown-ссылки проверяет `rag lint`. |
| DOC-08 | Язык — русский. Имена из кода пишутся как в коде, в обратных кавычках. |
| DOC-09 | Документ правится тем же коммитом, что и изменение, которое он описывает. |
| DOC-10 | Заголовки H2 и H3 содержательны, раздел понятен без соседних: поиск режет документы по этим заголовкам и отдаёт раздел отдельно. |

## 5. Процесс задачи

| ID | Правило |
|---|---|
| WORK-01 | Начало: `context_for_paths` по файлам, которые будут меняться или создаваться; для незнакомой области — `search`, затем `get` нужных разделов. Код прототипа — не образец. |
| WORK-02 | Правило GDD неясно, документы противоречат друг другу или решения нет — остановиться и спросить человека. Не додумывать. |
| WORK-03 | План живёт в разговоре (режим планирования), не в файлах. |
| WORK-04 | Изменение — одним атомарным коммитом вместе со всеми документами, которые оно затрагивает: CODE-16, CODE-17, CODE-19. |
| WORK-05 | Проверка перед ревью: компиляция и тесты Unity (`CodeStructure.md` §9, §12), `rag lint --changed` без ошибок. |
| WORK-06 | Перед каждым коммитом с кодом или документами — агент `reviewer` на изменения. Замечания исправляются; с неверным замечанием агент не спорит молча, а выносит его человеку. Коммит — после вердикта «чисто». |
| WORK-07 | Баг исправляется в первопричине: не глушить ошибку, не ослаблять проверку, не расширять допустимые состояния. Неочевидный урок бага — строкой `Нельзя: … — потому что …` в записи заметки. |
| WORK-08 | Агент ошибся из-за пробела в харнессе или документах — пробел закрывается правкой этого документа, `CLAUDE.md` или канонического документа, а не памятью сессии. |

## 6. Роадмап

`Docs/Roadmap.md` — единственное место статуса реализации; статусы и формат строки — в его шапке, когда обновлять —
CODE-17. Состав и этапы фич `rag lint` сверяет с `Docs/GDD/Features.md`.

## 7. Ревьюер

Общий промпт ревью — `.claude/agents/reviewer.md`: метод, условия действительного замечания и формат вердикта.
Claude использует агента `reviewer`, Codex — skill `rtp-reviewer` в отдельном контексте; без делегирования явно
отмечается самостоятельное ревью. Вход: задача и причина, ID фич, база Git, список файлов (включая новые),
результаты проверок и ограничения. Настройки модели и инструментов во frontmatter агента относятся к Claude.
Когда запускается — WORK-06; ревью само не даёт разрешения на коммит.

## 8. Проверки и хуки

`rag lint` — детерминированные проверки (`--changed` — только изменения относительно `--base`, по умолчанию `HEAD`):

| Код | Уровень | Проверка |
|---|---|---|
| `COMMENT` | ошибка | Комментарий в `.cs`, `.uss`, `.uxml`, шейдере (CODE-18) |
| `NOTE-MISSING`, `NOTE-ENTRY` | ошибка | У `.cs` нет заметки или записи о его типе (CODE-19) |
| `NOTE-STALE` | ошибка / предупреждение | Запись H3 (или строка таблицы) о типе, которого нет |
| `NOTE-FM` | ошибка | В шапке заметки id GDD, которого нет; неизвестный ключ — предупреждение |
| `NOTE-SYNC` | предупреждение | Код изменён, его заметка — нет (только `--changed`) |
| `BURST` | ошибка | `ISystem` без `[BurstCompile]` и без `Исключение ARCH-06` в записи |
| `LINK` | ошибка | Битая относительная ссылка в документе базы, `CLAUDE.md`, `AGENTS.md`, агенте или проектном skill |
| `MD-PLACE` | ошибка | Новый `.md` вне разрешённых мест (DOC-06, только `--changed`) |
| `ROADMAP` | ошибка | Роадмап расходится с `Docs/GDD/Features.md`: фича пропущена, повторена, не в своём этапе, неверный статус |

Разрешённые места `.md`: `CLAUDE.md`, `AGENTS.md`, `.claude/agents/`, `.agents/skills/*/SKILL.md`, `Docs/Roadmap.md`, `Docs/GDD/`, `Docs/GDD/Features/`,
`Docs/Tech/Harness.md`, `Docs/Tech/Architecture/`, `Docs/Tech/Reference/`,
`Docs/Parked/`, заметки `README.md` в `Assets/_Project/Code/` и `Assets/_Project/Features/`, `Configs/`.

Хуки (`.claude/settings.json`, скрипт `.claude/hooks/harness.py`):

| Событие | Что делает |
|---|---|
| `SessionStart` | Запоминает `HEAD` начала сессии |
| `PostToolUse` на `Read` `.cs` | Добавляет в контекст запись заметки о типе файла или сообщает, что записи нет |
| `PostToolUse` на `Edit`/`Write` `.cs` | Напоминает, какую запись обновить; для кода прототипа — предупреждает, что его не трогают |
| `Stop` | `rag lint --changed` от `HEAD` начала сессии; при замечаниях возвращает их агенту. Один и тот же набор замечаний повторно не возвращается, всего — не больше трёх раз за сессию |

## 9. Инструмент `Tools/rag`

- Python 3.12, зависимости через `uv` (`Tools/rag/pyproject.toml`). MCP-сервер подключён в `.mcp.json`.
- Индекс — `Tools/rag/.index/` (SQLite: разделы, FTS5, векторы), не в git. Эмбеддинги — локальная модель
  `BAAI/bge-m3` (1024 измерения, кэш `~/.cache/huggingface`), документы никуда не уходят. Первый запуск на новой
  машине — `uv run --project Tools/rag rag index` (скачивание модели ~2 ГБ и векторизация ~1–2 мин).
- Нарезка: по H2 и H3; раздел длиннее 3500 символов делится по абзацам, пунктам и строкам таблиц с повтором шапки.
- Модули: `common.py` (корпус, слои, разбор markdown, правила), `notes.py` (заметки к коду), `context.py`
  (`context_for_paths`, `get`, `related`, граф), `lint.py`, `index.py`, `search.py`, `server.py`, `cli.py`. Хуки и
  `lint` не зависят от модели и работают на системном `python3`.
- `context_for_paths` для `Tools/`, `.claude/`, `.codex/`, `.agents/` и входных инструкций выдаёт правила
  `DOC`, `WORK` и раздел этого документа; исходники инструментов читаются отдельно. Ошибка Git при выборе
  изменённых файлов прерывает lint, а не превращается в результат «замечаний нет».
- Новый слой или папка корпуса — строка в `CORPUS` (`common.py`, слой сразу попадает в поиск) и строка в §1. Новый
  префикс правил контура — `RULE_DOCS` и `CONTOUR_RULES`.
- Качество поиска — эталонные запросы `Tools/rag/eval/golden.yaml`, `rag eval` (порог hit@5 ≥ 80 %). Поиск не нашёл
  то, что должен был, — запрос с ожидаемым документом добавляется в эталон.

## 10. Инструмент `Tools/art`

Генерация картинок-ассетов в стиле [ArtStyle.md](../GDD/ArtStyle.md).

- Рисует встроенный `image_gen` доступного клиента Codex на подписке владельца; API-ключ для этой цепочки
  не нужен. Скрипт подготовки — системный `python3`, без зависимостей. Встроенный инструмент проверяется по
  фактически доступным tools; наличие исполняемого `codex` не доказывает доступность генерации.
- Команда: `python3 Tools/art/art.py "<описание по-английски>" --out <путь.png> [--size 2048x2048] [--transparent]
  [--ref <файл>]… [--style-ref <файл>|none] [--feature <ID>] [--force] [--dry-run|--request-json] [--queue]`; очередь —
  `--pending`, `--run-pending`.
- `--request-json` не генерирует: возвращает `prompt`, `transparent_background`, абсолютные пути `references`
  с ролями `style`/`subject`, `out`, `feature`. Codex просматривает референсы и передаёт эти данные встроенному
  инструменту по его фактической схеме. Полученный файл сохраняется в `out` с сохранением альфы; существующий
  файл заменяется только при выбранном `--force`. Это общий промпт с CLI-путём, а не второй стилевой шаблон.
- Без флагов подготовки скрипт запускает `codex exec` в отдельном временном каталоге с копиями референсов;
  нужны установленный CLI и выполненный владельцем `codex login`. `--dry-run` показывает задание этого пути.
  Он нужен клиентам без встроенного инструмента, в том числе Claude; установки и вход не выполняются скрыто.
- Стилевой блок скрипт берёт из `ArtStyle.md` (раздел «Стилевой блок промпта») и прикладывает эталон
  `Docs/References/Assets/1 Chosen style/1 style final.png`. `--style-ref` — другой эталон стиля вместо него:
  для окружения — эталон этажа (`ArtStyle.md` → «Эталоны этажей»); `none` — без эталона, только для проб. `--ref` — референс сюжета: например,
  спрайт существа для листа частей рига.
- Один вызов — один ассет. Размер в запросе положительный и кратен 16; размер результата измеряется отдельно,
  модель не гарантирует запрошенное разрешение. Время и доступный лимит зависят от клиента и подписки.
  CLI не публикует результат без PNG-заголовка/ненулевого размера или без запрошенного альфа-канала;
  таймаут возвращает ошибку, прежний ассет сохраняется. Полная проверка изображения остаётся за агентом.
- Лимит подписки исчерпан — скрипт сам ставит задание в очередь `Tools/art/pending.jsonl` и выходит с кодом 3.
  Остальные ассеты фичи агент ставит туда же (`--queue`): одно задание на ассет, с полным описанием, размером,
  путём, референсами и `--feature`. Фича продолжается на заглушках (`Content.md` §9); очередь коммитится вместе с
  фичей; в отчёте человеку — сколько ассетов ждёт в очереди. Лимиты восстановились — `--run-pending`: выполненные
  задания уходят из очереди, задание без `--force` с уже существующим файлом снимается.
- Что нельзя писать в описании — `ArtStyle.md` → «Генерация ассетов».
- Результат — кандидат: агент открывает его доступным просмотрщиком изображений и сверяет со стилем, размером и прозрачностью. Неудачный —
  новая генерация, а не правка результата.
- Куда класть и как называть ассет в проекте — `Content.md` §9.

## 11. Звуки: библиотека и `Tools/sfx`

Порядок поиска звука: библиотека [zvukipro.com](https://zvukipro.com) (бесплатные записи, личное использование
разрешено) → генерация ElevenLabs → локальная модель. Почему: записи библиотеки — настоящие; локальная модель на
большинстве звуков звучит неестественно (оценка владельца на пробе из 56 звуков).

- Библиотека — `python3 Tools/sfx/library.py`: `search "<запрос по-русски>" [--page N]` — подборки;
  `list <url подборки> [--probe]` — звуки подборки с названием, размером, числом скачиваний, с `--probe` — частота,
  каналы, битрейт и `ok`; `get <url mp3> --out <путь.wav> [--force]` — скачать и обработать: подрезка тишины,
  затухания, громкость. Годен исходник от 44,1 кГц и от 56 кбит/с на канал; ниже — скрипт предупреждает, такой не
  брать. Выбирать по названию и качеству; для заметных звуков — 2–3 варианта, выбор на слух за человеком.
- Генерация — `python3 Tools/sfx/eleven.py "<описание по-английски>" --out <путь.wav> [--duration 0.5–30]
  [--influence 0–1] [--loop] [--variants N] [--reverb 0–1] [--lowpass Гц] [--force]`; `--credits` — расход
  кредитов и дата сброса. Облачная модель ElevenLabs Sound Effects v2 по API; ключ владельца —
  `~/.config/elevenlabs/api_key`, вне репозитория: репозиторий публичный. Скрипт — системный `python3`, для обработки
  нужны `uv` и `ffmpeg`. Обработка — как у звуков библиотеки; `--loop` — бесшовная петля (эмбиент): без подрезки,
  фильтров, отзвука и затуханий, поэтому вместе с `--reverb` и `--lowpass` не задаётся. Без `--duration` длину выбирает модель; каждый вариант — отдельная генерация.
- Скрипт запрашивает mp3 44,1 кГц 128 кбит/с; фактический расход каждого результата берётся из ответа API.
  Баланс проверяется отдельно через `--credits`: его недоступность не скрывает успешно созданные файлы.
  Тариф и доступность подтверждаются аккаунтом, не фиксируются как постоянные свойства инструмента.
- Локальная генерация (ElevenLabs недоступен) — `python3 Tools/sfx/sfx.py "<описание по-английски>" --out <путь.wav>
  --kind noise|voice|impact [--duration 3] [--single] [--variants N] [--candidates N] [--seed N] [--reverb 0–1]
  [--lowpass Гц] [--force]`. Модель Stable Audio 3 Small SFX (движок `~/.cache/stable-audio-3`,
  `python3 Tools/sfx/sfx.py --setup`, нужны `uv`, `git`, `ffmpeg`; веса ~3 ГБ — из зеркала
  `FatalErrorVXD/stable-audio-3-small-sfx`). Готовый файл обрабатывается так же: `sfx.py --input <файл> --out …
  [--loop] [--offline]`. `--loop` допустим только с `--input`, без `--reverb` и `--lowpass`.
  Движок запускается с `uv --no-sync`; подготовка его окружения — отдельный `--setup`. Обработка закреплена
  на numpy 2.5.3, scipy 1.18.1 и soundfile 0.14.0. `--offline` запрещает сеть и скачивание Python/моделей,
  использует только кэш; без нужного кэша команда завершится ошибкой. `uv --with` может создавать окружение
  из кэша; при запрете любых установок передай `--processing-python <готовый-python>` с установленными
  numpy/scipy/soundfile. Переменная `RTP_SFX_PYTHON` задаёт тот же путь для обработки в дочерних вызовах
  `library.py` и `eleven.py`, не передавая ключей в аргументах. Для библиотечной/облачной цепочки
  офлайн-настройки применяются только к локальной обработке, сами источники требуют сети.
- Локальная модель подмешивает постоянные тоны на всех частотах — на слух пищание. Скрипт ресинтезирует каждый
  сгенерированный ею звук: рисунок громкости по частотам (шаг ~3 мс, сглажен по частоте) собирается заново из чистого
  шума. `--kind`: `noise` — весь звук (шорохи, шипение, жужжание, ветер); `voice` — выше 4 кГц (голоса, стоны);
  `impact` — выше 6 кГц (удары, металл, предметы). Нельзя: шумоподавление и вырезание полос (шипящие становятся
  неразборчивыми), замена только верха выше 9 кГц (пищание ниже остаётся).
- Описание для генерации — как подпись к звуку из библиотеки: источник, материал, действие, пространство; одно
  событие — «one single event». У локальной модели: `--single` и «…, then silence»; «clicks» даёт клавиатуру —
  насекомых описывать через «chittering, buzzing, hissing»; магические звуки она не умеет — их агент синтезирует
  слоями (тоны-колокольчики, фильтрованный шум, отзвук).
- Пустой, полностью беззвучный, нечисловой вход и записи короче 64 сэмплов отклоняются обработчиком.
  Агент без аудиопрослушивания проверяет длину и форму по спектрограмме; на слух качество подтверждает человек.
- Одобренные образцы — `Docs/References/Assets/6 Sounds/`. Куда класть и как называть звук в проекте — `Content.md` §9.

## 12. Инструмент `Tools/layout`

Прототип генератора этажей по концепту `W02`, `W11` R32: граф угодий, формы по материальности этажа, перевалы,
точки интереса; проверка — проходимость тела 1,6 клетки, у каждой локации ≥ 2 нетайных перевала, обход у заставы,
печати и опасного перевала (`W16` R23), тайный — сверх них; переход вверх — в дальних от старта локациях (`W03` R15). Рисует схемы — эталонные планировки Среза
(`Docs/References/Assets/1 Chosen style/Layouts/`, `W02`); кодом игры не является.

- Команда: `uv run -p 3.12 --with numpy==2.5.3 --with scipy==1.18.1 --with pillow==12.3.0 python
  Tools/layout/floors.py <папка> [seed]` — схемы семи этажей; `… python Tools/layout/overview.py <папка>` — общий
  лист. Версии закреплены: другой numpy может дать другой поток случайных чисел и другие схемы.
  Эталонные планировки — seed 5; другой seed — другие вариации. Генератор создаёт выходную папку.
  Для проверки используй временную папку: повторный запуск перезаписывает одноимённые PNG. Общий лист требует
  все семь готовых схем. Для работы из кэша добавь к `uv run` флаги `--offline --no-python-downloads`.
- Проверка: `… python Tools/layout/floors.py bench <число>` (с теми же `uv run`) — собирает столько этажей каждого вида и печатает
  попытки и время.
- Параметры этажей — словарь `FLOORS` в `floors.py`; меняются вместе с `W11` R32 и `W02` §5.


## 13. Codex рядом с Claude Code

### 13.1. Инструкции, skills и промпты

Общая база знаний, правила, заметки и `Tools/rag` используются обоими агентами. Конфигурации Claude —
`.claude/` и `.mcp.json`; Codex — `.codex/config.toml`, `.codex/hooks.json`, `.agents/skills/`.
`CLAUDE.md` задаёт общие нормы, `AGENTS.md` — применение в Codex и границы разрешений.
Глобальные разрешения одного агента другому не передаются; одновременную правку одного файла согласовывают.

| Элемент Codex | Назначение и источник |
|---|---|
| `rtp-reviewer` | Адаптер общего промпта ревью §7; чтение и проверка, без исправлений |
| `rtp-unity-mcp` | Выбор экземпляра редактора, операции, компиляция, тесты и проверка результата |
| `rtp-assets` | Выбор цепочки §10–12 и передача кандидата в игру (§14) |
| Промпт изображения | `ArtStyle.md` → `Tools/art/art.py`: один стилевой блок для встроенного инструмента и CLI |
| Промпт звука | Конкретный источник, материал, действие, пространство по §11; параметры и seed — в запросе CLI |
| Схемы этажей | `Tools/layout/floors.py`: параметры `FLOORS`, seed и нормы W02/W11; текстовый промпт не используется |

Skills обнаруживаются клиентом в `.agents/skills/*/SKILL.md`; если список в текущем чате устарел, агент читает
файл напрямую. Архивы миграции и глобальные skills пользователя не являются обязательными зависимостями проекта.

### 13.2. MCP и доступность операций

Проектный сервер в `.mcp.json` и `.codex/config.toml` — `rag`. Codex запускает `rag.server` существующим Python
из `Tools/rag/.venv`, без установки зависимостей; модель bge-m3 берётся из локального кэша, скачивание отключено.
Пути команды и `cwd` привязаны к workspace владельца: при переносе проверяются диагностикой §13.4.
Пять операций — §2; префикс имени инструмента зависит от клиента. Успешный `get` проверяет точную выдачу,
`search` — также индекс и модель, `context_for_paths` — маршрутизацию правил, `related` — граф, `lint` — проверки.

Пакет `com.coplaydev.unity-mcp` объявлен в `Packages/manifest.json`, но проектного подключения Unity MCP
в Codex нет. Подключение выполняется по фактическим настройкам установленного сервера после разрешения работы
с редактором; endpoint не угадывается. Наличие пакета не подтверждает работающий сервер.
Чужие MCP из продакшн-проекта и личные плагины не входят в харнесс игры и автоматически не подключаются.
Создание ассетов через §10–12 не требует отдельного MCP: используются встроенный image tool или CLI.

### 13.3. Адаптер hooks

`.codex/hooks/harness.py` вызывает функции `.claude/hooks/harness.py`, сохраняя проверки §8.
Состояние Codex хранится отдельно в системном временном каталоге `rtp-codex-harness`, по проекту и session ID.
Отсутствующий session ID — ошибка; повторный SessionStart сохраняет исходную базу. Без базы Stop проверяет
рабочее дерево от HEAD и явно предупреждает, что коммиты сессии не покрыты.

PostToolUse принимает shell как `Bash`, `apply_patch` с `tool_input.command`, прямые file/path аргументы;
учитывает quoted paths, workdir, переносы в patch и фактические изменённые/удалённые C# файлы.
Подсказки объединяются в один JSON. Вычисляемые пути и `cd` внутри shell могут скрывать чтения;
`context_for_paths` перед правкой остаётся обязанностью агента. Stop использует ограничение повторов §8.

Hooks требуют доверия точному определению через `/hooks`; при изменении определения клиент требует повторного
просмотра. Конфигурация и ручной тест адаптера не доказывают автоматический запуск: в клиенте проверяются
фактические события SessionStart, PostToolUse и Stop. Состояние событий — локальный `events.jsonl` рядом с базами
сессий; в нём только тип события и хеш session ID. Unity и игровые тесты hooks автоматически не запускают.
Поведение событий сверяется с [официальной документацией Hooks](https://learn.chatgpt.com/docs/hooks).

### 13.4. Проверки без Unity и генерации

Команды из корня проекта; они не устанавливают зависимости и не обращаются к поставщикам ассетов:

```sh
Tools/rag/.venv/bin/python -B Tools/harness/check.py
python3 -B Tools/harness/test_harness.py
PYTHONPATH=Tools/rag Tools/rag/.venv/bin/python -B -m rag.cli lint --changed
PYTHONPATH=Tools/rag Tools/rag/.venv/bin/python -B -m rag.cli lint
PYTHONPATH=Tools/rag HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 Tools/rag/.venv/bin/python -B -m rag.cli eval
```

Диагностика проверяет конфигурации, пути, референсы,
известные зависимости, ссылки и lint; ключ ElevenLabs проверяет только на существование, не читает его.
`unverified` обозначает непроверенную возможность, а не успех. Статические проверки не заменяют соединение,
аутентификацию и вызов сервиса. Ошибки завершают диагностику ненулевым кодом.

Тесты используют временные файлы и подменяют внешние вызовы: сессии/hooks, подсказки, lint при ошибке Git,
промпт/очередь/отказ публикации изображения, параметры звука и результат ElevenLabs. Числовые тесты звука
требуют уже установленных numpy/scipy/soundfile и явно пропускаются без них; для полной проверки запускай
тем Python, где они установлены. Отдельно проверяется обработка готового WAV и генерация схем в временный каталог
с зависимостями §11–12; никаких новых референсов эти прогоны не утверждают.

После изменения Python-модулей RAG уже работающий MCP-процесс нужно перезапустить средствами клиента;
новые файлы документов индексируются без перезапуска. После изменения skills/config проверь их обнаружение
клиентом. Локальный CLI проверяет код с диска и не доказывает обновление уже работающего MCP-процесса.

## 14. От кандидата до игрового ассета

Канонический маршрут хранения, имена, пресеты, атласы, группы и visual id — `Content.md` §9.
Детали ригов/анимации и VFX — `Presentation.md` §5, §9–10; UI — `UI.md`; строки и шрифты — `Content.md` §8 и UI.md.
Производство начинается с фичи, visual id, роли ассета, референсов и выходного пути. Кандидаты проверяются
до замены одобренных файлов; `.meta` и GUID сохраняются, чужие незавершённые изменения не перезаписываются.

| Цепочка | Что проверяется до завершения |
|---|---|
| Концепт/спрайт/текстура → части → PSB/риг/клипы → префаб | Промпт и эталон §10, видимые свойства ArtStyle.md, фактические размер/альфа/швы; затем скелет, крепления, Sprite Library и анимации в Unity |
| Звуковой источник → WAV → AudioClip | Источник и качество §11, длительность, пик, каналы, стык петли; прослушивание человеком; пресет и воспроизведение в Unity |
| Схема этажа → общий лист | Проверки графа и проходимости §12, визуальная читаемость; схема остаётся референсом, не шаблоном игровой комнаты |
| UXML/USS, VFX, материалы, шейдеры | Компиляция/импорт, внешний вид в целевом UI/сцене и бюджет по документу контура; картинка сама по себе не создаёт эти ресурсы |
| Локализация, музыка, шрифты | Источник, разрешённое использование и проектный формат; для музыки/шрифтов отдельный генератор харнессом не объявлен, для строк — путь импорта Content.md §8 |
| Ассет → Addressables → visual id | Пресет, адрес/группа/метки, отсутствие дублей, разрешение visual id и фактическая загрузка; проверки Content.md §9 |

Готовность редакторов, импортёров, AddressRules и пакера проверяется по `Docs/Roadmap.md` и наличию реализации.
Не существующие ещё инструменты нельзя объявлять выполненными шагами. Если Unity-этап недоступен, результат —
проверенный кандидат с перечисленными оставшимися операциями; фича не отмечается завершённой.
В итог задачи входят пути результатов, измеренные характеристики, выполненные/пропущенные проверки и очередь.
